# Authentication — Phase 02

## User experience
- Passwordless one-time codes sent by email or SMS.
- Phone numbers must use E.164 format (for example, +947XXXXXXXX).
- Each user chooses a display name and unique username.
- Postgres generates a public ID for each profile.

## Supabase setup
1. Configure the app URL and publishable/anon key using the `--dart-define` values in the README.
2. Enable Email and Phone providers in Supabase Authentication.
3. For email OTP codes, edit the Magic Link email template to include `{{ .Token }}`. Otherwise the default template may send a magic link instead of a code.
4. Configure an SMS provider before enabling phone sign-in. SMS OTP will not work until this is configured.
5. Run `supabase/setup_profiles.sql` in the Supabase SQL Editor.
6. Test delivery with accounts and phone numbers you control.

## Profile data and privacy
The app uses only `public.apm_profiles`, namespaced to avoid collisions with unrelated applications in the shared Supabase project. RLS is enabled; users can read and insert only their own profile row. Public IDs are generated by Postgres, and usernames are case-insensitively unique.

## Important notes
- Supabase Auth's OTP flow may automatically create an Auth user when an OTP is requested for a new contact.
- Existing profile rows are not overwritten during sign-in.
- Phone numbers can be recycled. Verify ownership and consider enabling MFA before production launch.
- Never put service-role keys or SMS provider secrets in Flutter code.
- Configure production SMTP, SMS delivery, redirect URLs, rate limits, and abuse protection before public release.

## Verification checklist
- Email OTP request and verification.
- SMS OTP request and verification with a configured provider.
- Duplicate username rejection.
- A user cannot read another user's profile through the Data API.
- Sign-out clears the local session.
